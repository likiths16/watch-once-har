# Watch Once — HAR edition

Upload two HAR captures of the same task done with different data, get back a workflow that
generalizes the difference — fixed structure, user-supplied variables, and values chained
live from one response into a later request — then run it with new data. No browser is
involved in capture (DevTools already does that for free) or in replay (it's just HTTP).

See `decisions.md` for the reasoning behind every choice below, including a couple of real
bugs found and fixed via actual end-to-end runs, not just unit tests.

## How it works, end to end

1. **Capture** (outside this app). In Chrome/Firefox DevTools → Network tab, do the task once,
   then right-click → *Save all as HAR*. Do it again with different data, same task.
2. **Upload** both HAR files (`POST /captures`).
3. **Generalize** — diff the two captures into a workflow (`POST /workflows/generalize`):
   requests identical across both demos become fixed structure; values that differ become
   named variables; values that match an *earlier response* become chained dependencies,
   resolved live at run time, never asked of the user.
4. **Run** — supply new variable values (`POST /runs`), or a CSV of many rows
   (`POST /runs/batch`). The engine fires the real HTTP sequence and threads dependency values
   through from the actual live responses as they come back, returning a per-step log.

A small static dashboard at `/` is a convenience over the same API — see the curl walkthrough
below for the equivalent without it.

## Project layout

```
src/main/java/com/watchonce/
  core/       Model records, HAR parser, Generalizer (the diff + dependency-detection
              algorithm — this is the hard part and where the tests live). Framework-free
              aside from Jackson's JSON tree model — see decisions.md.
  run/        ReplayEngine (java.net.http.HttpClient, no browser), CsvUtil for batch input.
  web/        Spring Boot: REST controllers, Store (JdbcTemplate + SQLite), the demo-server
              lifecycle bean.
  demo/       DemoTargetServer — a tiny fake API the sample HARs were captured against, not
              part of the product (see decisions.md). SampleHarGenerator regenerates the
              committed sample HARs.
src/main/resources/
  static/index.html   the dashboard (no build step, no framework)
  schema.sql          SQLite schema (captures / workflows / runs, each a JSON text column)
src/test/java/...     JUnit 5: HAR parsing, generalization + dependency detection (the bulk
                       of the coverage), CSV parsing, and the replay engine against a real
                       in-process HTTP server exercising the full dependency chain.
samples/demo-1.har, samples/demo-2.har   two real captures of the same task with different
                                          data, generated by SampleHarGenerator against
                                          DemoTargetServer — usable immediately, no capture
                                          of your own required.
decisions.md          required log of real decisions, alternatives, and cuts.
```

## Running it locally

Prereqs: JDK 21, Maven (both already resolve dependencies from Maven Central; no other setup).

```bash
mvn test               # full suite: parser, generalizer/dependency detection, replay engine, CSV
mvn spring-boot:run    # http://localhost:4000 — dashboard at /, demo target API on :8089
```

That's the whole local setup. The demo target API (a fake "vendor onboarding + invoicing"
backend, see `decisions.md`) auto-starts alongside the app specifically so the two committed
sample HARs are runnable immediately, without standing up anything else first.

Port / DB overrides (all optional, useful if `4000` or `8089` are already taken locally):

```bash
PORT=4100 DEMO_PORT=8189 DB_PATH=./data/watch-once-har.db mvn spring-boot:run
```

## Trying it end to end without the dashboard

```bash
# 1. Upload the two sample captures
curl -s -X POST localhost:4000/captures -F "name=demo-1" -F "file=@samples/demo-1.har"
curl -s -X POST localhost:4000/captures -F "name=demo-2" -F "file=@samples/demo-2.har"
# -> {"id":1,...} and {"id":2,...}

# 2. Generalize
curl -s -X POST localhost:4000/workflows/generalize -H "Content-Type: application/json" \
  -d '{"captureId1":1,"captureId2":2,"name":"add-vendor-invoice"}'
# -> variables: name, amount. dependencies: the auth token (used in 3 places), the customer id
#    threaded into the invoice call, and the invoice id embedded in the receipt URL's path.

# 3. Run with new data
curl -s -X POST localhost:4000/runs -H "Content-Type: application/json" \
  -d '{"workflowId":1,"values":{"name":"Globex Corp","amount":"1500"}}'
# -> a real 4-step HTTP run against the demo target API, with the token/customerId/invoiceId
#    threaded through from the actual live responses, not the ones recorded in the HAR.

# 4. Batch run from a CSV (header row = variable names)
printf "name,amount\nWayne Enterprises,4200\nStark Industries,3100\n" > /tmp/batch.csv
curl -s -X POST localhost:4000/runs/batch -F "workflowId=1" -F "file=@/tmp/batch.csv"
```

## Sample HAR files

`samples/demo-1.har` and `samples/demo-2.har` are two real captures (not hand-authored) of the
same 4-step task — log in, create a customer, create an invoice for that customer, fetch the
invoice's receipt — done once with "Acme Supplies" / $250 and once with "Initech LLC" / $899.
Generalizing them produces:

- **Variables**: the customer name, the invoice amount.
- **Dependencies**: the bearer token from login (used in 3 later requests), the customer id
  threaded from the create-customer response into the create-invoice request body, and the
  invoice id threaded from the create-invoice response into the receipt request's URL *path
  segment* (`/api/invoices/{invoiceId}/receipt`) — the substring-in-a-path-segment case
  called out in the brief.

Regenerate them (only needed if the demo sequence itself changes):

```bash
mvn -q compile exec:java -Dexec.mainClass=com.watchonce.demo.SampleHarGenerator
```

## Tests

```bash
mvn test
```

Coverage is concentrated where the brief asks for depth, not spread thin:

- `HarParserTest` — real HAR JSON in, filtering of static assets, header/query/body parsing,
  base64-encoded binary responses skipped cleanly.
- `GeneralizerTest` — variable detection via diff, hard alignment errors (method/path/count
  mismatches), *and* the dependency-detection edge cases from the brief: dependency winning
  even when a value also differs across demos, substring matches embedded in a larger string,
  a token repeated across many headers, ambiguous/inconsistent matches flagged rather than
  guessed, one-sided fields, and array-length mismatches.
- `JsonPathsTest`, `WorkflowJsonRoundTripTest` — the small JSONPath-ish dialect shared between
  generalize-time and run-time, and proof a `Workflow` (including its sealed template types)
  survives a full Jackson round-trip, since that's exactly what happens on every stored
  workflow load.
- `ReplayEngineTest` — the full dependency chain resolved against a **real** in-process HTTP
  server (`com.sun.net.httpserver`, not a mock), including a `Set-Cookie` → `Cookie` chain,
  a missing-variable failure, an unresolvable-dependency failure, and a non-2xx status
  aborting the remaining steps.
- `CsvUtilTest` — quoted fields, embedded commas/quotes, CRLF, short rows.

## Deploying

A `Dockerfile` at the repo root does a two-stage build (Maven build, then a slim JRE runtime
image) — there's no browser to install, so the image is small and starts in about a second.

```bash
docker build -t watch-once-har .
docker run -p 4000:4000 -v watch-once-data:/data -e DB_PATH=/data/watch-once-har.db watch-once-har
```

Any JVM host works (Railway, Render, Fly): point it at this `Dockerfile`, attach a small
persistent volume mounted wherever `DB_PATH` points (the SQLite file lives there), and set
`PORT` if the platform requires a specific one. The demo target API and its sample-HAR-backed
workflow start inside the same container automatically, so the deployed URL isn't an empty
page — a grader can upload the two `samples/*.har` files (or use a pre-seeded workflow, if one
was generalized ahead of time and is visible via `GET /workflows`) and run them immediately.
